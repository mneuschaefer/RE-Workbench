# Use cases

This is an example and a placeholder for the project's own RE method. Read available project guidance before applying it. Project terminology, templates, review criteria and explicit user instructions take precedence. Adapt or replace this skill when requested; do not present its example structure as a mandatory standard. Additional project-specific tools and skills may be used where applicable.

Read `AGENTS.md` and the selected working files. Use `2 Templates/Use case.md` for a new use case. Keep an existing structure if it already makes the flow clear.

Identify the primary actor, goal, trigger and any stated preconditions. Describe the interaction as numbered actor and system steps. Separate the successful outcome from alternatives and failures, and tie each branch to the step that triggers it. State whether the flow resumes, ends or leaves a changed state.

Use only supported business rules. Keep missing permissions, exceptions or recovery rules as open questions instead of inventing them. Avoid prescribing screens or technical internals unless the source or user requires them. Preserve source attribution and write in the source language unless asked otherwise.

Edit the selected files under `1 Working files`; never change downloaded sources or internal identity. For a review request, identify missing outcomes, ambiguous steps and unsupported assumptions before rewriting unless editing was requested. Keep the result proportional to the scenario. Report affected files and unresolved decisions. Publishing requires a separate user request under the Confluence workflow skill.
