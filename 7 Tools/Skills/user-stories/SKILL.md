# User stories

This is an example and a placeholder for the project's own RE method. Read available project guidance before applying it. Project terminology, templates, review criteria and explicit user instructions take precedence. Adapt or replace this skill when requested; do not present its example structure as a mandatory standard. Additional project-specific tools and skills may be used where applicable.

Read `AGENTS.md` and the selected working files. Use `2 Templates/User story.md` when starting a new story; preserve a useful existing structure when reviewing one.

Keep the user's role, need and intended benefit clear. Acceptance criteria should describe observable outcomes, including relevant permission, validation or failure cases supported by the source. Do not invent policy, thresholds, roles or product decisions. Mark missing decisions as open questions; distinguish proposed assumptions from confirmed requirements.

Keep each story about a coherent user outcome. Suggest a split when independent outcomes need separate decisions or tests, but do not turn every implementation step into a story. Preserve source links and identifiers. Write in the source language unless asked otherwise.

Edit only the selected files under `1 Working files`. Put unrelated private questions in `4 Notes`; do not modify downloaded sources or internal identity. For a review request, report concrete gaps before rewriting unless the user asked for edits. Finish with the affected files and unresolved decisions. Publishing requires a separate user request under the Confluence workflow skill.
